## 6 项 Notes（非阻塞，实施时修）

### N1 · P0：路网数据验证缺失（最致命发现）

**问题**：OSM 武大校园路网覆盖不足是整个项目最可能推翻一切假设的单点故障。TDD §18 的 todo 直接写代码，没有把"先跑一遍数据验证"作为第一步。

**风险**：
- 若 OSM 在武大 footway 覆盖率 < 50%，DEC-007 的高德+OSMnx 双坐标系方案需要推翻
- 若关键路径（如樱顶→老图书馆）在 OSM 中不存在，多因素路径规划无法工作
- R3（OSM 武大校园路网缺失）在 TDD §14 已标记，但应对方案"手动补段或降级为高德路径 API"未量化

**实施要求**：
- Stage 4 **第一步**：编写 `scripts/validate_osm_network.py`，量化验证 OSM 路网覆盖
- 验证指标：
  1. 武大核心区（WHU_BBOX）footway/path 路段总数
  2. 与 15 条 query 涉及的 POI 的路网连通性
  3. 关键路径（牌坊→樱顶、樱顶→老图书馆、教五→图书馆）是否存在通路
  4. 路段平均长度、最大长度、最小长度
- 验证结果需输出覆盖率报告，≥ 80% 方可进入编码阶段
- 若 < 80%：立即启动降级方案（补充关键路段或调整为高德路径 API）

### N2 · P1：硬约束过滤后路径可能极长，无上限保护

**问题**：DEC-011 硬约束过滤（如 `slope=avoid` 过滤 slope_level=5 路段）后，Dijkstra 可能绕极远的路。TDD 仅有兜底"若无可行路径则放宽"，但未限制路径长度上限。

**实施要求**：
- 在 `spatial/routing.py` 的 `compute_route()` 中增加路径长度上限保护
- 上限规则：推荐路线长度 ≤ 最短路径长度 × 3（或 ≤ 2000 米，取较小值）
- 超过上限时自动降级：放宽约束（如 slope_level=4 可通行加 3× 惩罚）
- 降级时在解释文本中标注"约束放宽，已为您找到可行路线"

### N3 · P2：LLM 调用无 timeout 保护

**问题**：DeepSeek API 单次 RTT 20-50ms + 推理 800-1500ms，理论上 P95 ≤ 3s。但极端网络情况（如跨境波动、服务端抖动）可能超时，导致整个请求链路阻塞。

**实施要求**：
- `agents/parser.py` 和 `agents/explainer.py` 的 LLM 调用增加 timeout 参数
- timeout 设置：connect=5s，read=10s（合计 ≤ 15s）
- 超时处理：捕获 `APITimeout` 异常，返回兜底结果（默认权重 + 错误提示）
- 日志记录超时事件，便于后续排查

### N4 · P1：场景 3 后端返回候选 → 前端选 → 自动重新规划，交互未闭环

**问题**：TDD §5.3 设计了场景 3（起点 + POI 类型）的候选算法，但后端返回候选 POI 列表后，前端如何展示、用户选择后如何触发重新规划，TDD 未定义完整交互链路。

**实施要求**：
- 后端 `/api/route` 增加 `candidates` 字段：当场景 3 触发时返回候选 POI 列表
- 候选列表包含：POI 名称、类型、路网距离、scenery_score
- 前端交互：以卡片列表展示候选，用户点击后自动触发重新规划（用选中的 POI 作为终点）
- 若无候选 POI（如该类型 POI 不存在），返回错误提示"该类型景点暂时无法找到"

### N5 · P2："避人流"在无数据下只是语义占位

**问题**：TDD §15 N3 记录了将"避开人流"映射为 `distance=relaxed` 的简化方案。但这个映射过于粗糙——用户说"避开人流"可能需要的是走偏僻路线而非绕远路。

**实施要求**：
- V1 简化实现：`crowd` 约束映射为 `distance=relaxed` + `scenery=any`（无偏好，走相对清静的路）
- 在解释文本中标注"已选择相对清静的路线"
- V2 改进方向：如果有 crowd 数据（路段人流量），可作为额外成本因素

### N6 · 优先级问题：快捷按钮与默认权重协同

**问题**：用户之前讨论过"快捷按钮 vs 默认权重"的矛盾——距离优先按钮触发 `weights={distance: 0.8, ...}`，但默认权重是 `{distance: 0.5, ...}`。如果用户先点了"景观优先"按钮，然后用 NL 输入"从 A 到 B"，应该用哪个权重？

**实施要求**：
- 优先级规则：**显式 NL 偏好 > 快捷按钮 > 默认权重**
- 具体实现：
  1. NL 输入含偏好表述 → LLM 生成 weights（覆盖一切）
  2. NL 输入无偏好 + 快捷按钮 → 用按钮预设 weights
  3. NL 输入无偏好 + 无快捷按钮 → 用 DEFAULT_WEIGHTS
- 前端实现：快捷按钮点击后高亮；NL 输入解析后，如果 LLM 生成了 weights，清除快捷按钮高亮
- 在解释文本中说明使用的偏好来源（"已按您的景观偏好推荐" / "已按默认路线推荐"）

## 设计总结

这份 TDD 的核心价值在于：

1. **方法创新性**：LLM → 空间认知 → GIS 决策 链路，比"AI 帮你规划路线"高级一个层次
2. **架构解耦**：agents/ 只管 LLM，spatial/ 只管 GIS，两层独立可测试
3. **决策可追溯**：11 条决策日志记录了每个关键选择的理由和放弃方案
4. **研究价值**：核心研究问题"LLM 能否作为人类空间偏好的转换器"适合本科科研论文

6 个 Notes 都是"锦上添花"的改进，不影响整体架构的正确性。最大的风险是 N1（路网数据验证），必须在编码前解决。
