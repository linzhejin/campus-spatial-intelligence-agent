# Agent 研究就绪：路线策略、画像与无损重算设计

**日期：** 2026-09-27

**适用项目：** 珞珈智行（WHU-Walker）

**目标：** 在正式论文实验前完成智能体核心能力收敛，使日常通勤、游览推荐、用户画像、策略切换和出行方式切换具有明确、可复现且不会污染上下文的语义。

## 1. 设计结论

采用“统一路线状态快照 + 确定性重算 + 分层偏好策略”的方案。

- 普通通勤使用真正的纯最短路径，不再把 `1/0/0` 当作普通多因素权重传入。
- 游览或明确推荐场景才使用多因素推荐；可靠画像存在时使用画像，否则使用平衡默认权重。
- “最短路径、风景优先、平坦优先”成为路线结果区的正式切换按钮。
- 切换策略或出行方式只改变被点击的字段，完整保留起终点、途经点、游览点、分段、硬约束和原始任务。
- 每次重算成功后原子更新路线结果和上下文；失败时保留上一条成功路线及全部状态。
- 先完成本设计定义的研究就绪门槛，再冻结代码、数据、模型和提示词，最后运行论文正式实验。

## 2. 当前问题与根因

### 2.1 权重语义不满足新要求

当前 `spatial/routing.py` 的默认权重为 `0.90/0.05/0.05`，且 `resolve_weights()` 会把每项限制在 `0.05~0.90`。因此把 `1/0/0` 作为普通权重传入，会被重新裁剪为接近 `0.90/0.05/0.05`，不能得到严格的纯最短路径。

### 2.2 路线切换会丢失任务结构

前端 `lastRouteRequest` 只保存 `start/end/constraints/weights`。切换步行、骑行或驾车时，前端直接调用 `/api/route`：

- 途经路线会退化为普通 A→B 路线；
- 游览路线会丢失游览点、顺序和环线信息；
- 多模式路线会丢失分段；
- 重算结果没有完整同步 `lastIntent` 和对话槽位，后续自然语言可能继续引用旧模式或旧需求。

偏好快捷操作还在使用旧 `/api/parse → /api/route` 链路，也没有与当前 Agent 状态同步。这是“点击出行方式或快捷键后需求退化、上下文错乱”的直接原因。

### 2.3 用户画像信号不可靠

当前前端把“路线展示 20 秒且未被覆盖”自动记为采纳。这会把用户没有主动选择的模型结果反向学习进画像，形成自我强化。普通通勤权重也可能持续把画像推向距离偏好，无法代表用户在游览场景中的真实选择。

### 2.4 路由实现存在重复开销

一次 `compute_route()` 会重复扫描或复制路网、重新归一化长度、准备方式图，并运行推荐与最短两次 Dijkstra。途经路线和游览路线又会逐段重复这些准备过程。校园图规模可以继续使用 NetworkX，但静态准备结果需要复用。

## 3. 被否决的替代方案

### 3.1 继续修补前端多个状态变量

改动较小，但 `lastRouteRequest`、`lastIntent`、`latestRoute` 和聊天历史仍然可能分离，无法建立可验证的不变量。

### 3.2 每次切换都重新调用 Agent 理解需求

接口形式统一，但模型可能重新解释地点、丢失途经点或改变任务类型。按钮切换属于确定性操作，不应依赖概率模型重新推理。

### 3.3 更换 OSRM、GraphHopper 或自研原生路由引擎

当前路网约 12,550 条边，Dijkstra 足以支撑校园规模。更换引擎会增加坡度、景观、动态管制和画像权重的适配成本，不能直接解决状态退化问题。

## 4. 任务分类与策略优先级

### 4.1 任务分类

路线请求先归入以下语义之一：

- `commute`：上课、回宿舍、去食堂、赶时间、普通 A→B 等到达型任务。
- `leisure`：游览、散步、赏樱、看风景、拍照、打卡、带朋友逛等体验型任务。
- `explicit_preference`：用户明确提出风景、平坦、避坡、最短等要求。

POI 类别只作为辅助证据。目的地是景点不能单独把普通“去某地”改成游览；需要结合游览动词、推荐意图、任务卡或 `plan_tour` 工具调用判断。通勤语言始终优先于目的地类别。

### 4.2 策略优先级

从高到低依次为：

1. 用户本轮自然语言明确要求或本轮点击的策略按钮；
2. 用户明确提出的硬约束；
3. `leisure` 场景下达到可信门槛的用户画像；
4. `leisure` 场景的平衡默认策略；
5. `commute` 场景的纯最短策略。

本轮显式选择只能覆盖软策略，不能取消“道路封闭、禁止通行、不要台阶、避开陡坡”等仍然有效的硬约束。

## 5. 路线策略定义

路线策略使用明确枚举，避免通过浮点权重猜测用户意图：

| 策略 | 距离/坡度/景观 | 使用条件 |
|---|---:|---|
| `shortest` | 语义等价于 `1.00/0.00/0.00` | 普通通勤、最短按钮、明确赶时间 |
| `recommended` | 画像；无可靠画像时 `0.50/0.20/0.30` | 游览、散步或明确请求推荐 |
| `scenery` | `0.50/0.10/0.40` | 风景优先按钮或同等自然语言 |
| `flat` | `0.50/0.40/0.10` | 平坦优先按钮或同等自然语言 |
| `custom` | 由明确自然语言生成，并受安全边界限制 | “远一点也可以，但尽量看景”等复合偏好 |

`shortest` 走独立长度最短分支，只运行一次最短路径搜索。它不经过 `resolve_weights()` 的 `0.05~0.90` 限制。

### 5.1 绕行上限

所有绕行比较都以同一出行方式、同一路况和同一硬约束下的可行最短路径为基线。

- `recommended/scenery/flat` 默认最大绕行比为 `1.25`；
- 用户明确表示“远一点没关系、以风景或平坦为主”时放宽到 `1.50`；
- 候选路线超过上限时，按固定插值序列把偏好权重逐步向纯距离收敛，选择满足上限且保留偏好最多的方案；
- 所有尝试仍超限时返回可行最短路线，并在结果中标记偏好因绕行上限被降级；
- 当前只记录 `length_capped=true` 但仍展示超长路线的行为被移除。

权重插值最多尝试四档，配合模式图预处理控制额外耗时。

## 6. 用户画像

### 6.1 使用范围

- 画像只参与 `recommended` 场景；
- `commute` 请求始终走 `shortest`，不读取游览偏好画像；
- 点击最短、风景或平坦按钮，以及本轮自然语言显式偏好，均高于画像；
- 画像距离权重不得低于 `0.40`，坡度或景观任一单项不得高于 `0.50`，归一化后再使用；
- 画像样本不足时回退到 `0.50/0.20/0.30`。

### 6.2 学习信号

取消“展示 20 秒即采纳”。改为：

- 策略按钮点击只记录 `strategy_selected`，作为待确认信号；
- 用户在该策略下点击“开始导航”时记录一次有效偏好采纳；
- 完成导航可记录更强的正向信号；
- 用户切换离开当前策略时记录 `strategy_abandoned`，不把被放弃策略写入画像；
- 普通通勤的纯最短结果不更新游览画像；
- 路线曝光仅用于产品统计，不参与 EMA。

画像记录同时保存样本数、最近更新时间和信号来源，使论文实验可以冻结或清空画像后复现。

## 7. 统一路线状态快照

每次成功路线都返回并保存一个规范化 `route_state`：

```json
{
  "schema_version": 1,
  "route_kind": "direct|via|tour|multimodal",
  "original_query": "用户原始需求",
  "start": {},
  "end": {},
  "via": {},
  "tour": {"pois": [], "loop": true},
  "legs": [],
  "travel_mode": "walk|bike|drive",
  "hard_constraints": {},
  "strategy": {
    "name": "shortest|recommended|scenery|flat|custom",
    "source": "commute_default|tour_default|profile|explicit_nl|button",
    "weights": {},
    "detour_cap": 1.25
  },
  "data_version": "校园数据指纹",
  "road_condition_version": "路况版本"
}
```

不适用于当前 `route_kind` 的字段为空。后端对客户端回传快照重新校验，只接受白名单字段，不信任客户端提供的计算结果、边序列或距离。

`route_state` 是路线重算和后续对话槽位的唯一事实源。前端不再分别从 `lastRouteRequest`、`lastIntent` 和渲染结果拼接任务语义。

## 8. 确定性重算

新增统一重算入口，输入上一条成功的 `route_state` 和单一变更：

```json
{
  "route_state": {},
  "change": {"travel_mode": "bike"}
}
```

或：

```json
{
  "route_state": {},
  "change": {"strategy": "scenery"}
}
```

后端按 `route_kind` 分派到 direct、via、tour 或 multimodal 的确定性规划函数，并保持其余字段不变。

### 8.1 状态提交规则

1. 前端发起重算时保留当前成功快照，按钮只进入加载态；
2. 响应返回后先校验 `requestSeq` 和 `route_state`；
3. 成功时一次性替换地图路线、结果卡、`route_state`、`latestRoute` 和对话规划槽位；
4. 失败时恢复按钮选中态，继续展示上一条成功路线；
5. 切换操作不伪造成用户自然语言，不向聊天历史写入虚假的 user/assistant 消息；
6. 更新后的结构化规划槽位必须包含最新出行方式和策略，使下一轮“还是走平坦点”“换回步行”等承接正确。

多模式路线的全局出行方式切换存在语义歧义，后端返回结构化澄清结果并保持原路线，不得静默把多段路线降级为普通直达路线。

## 9. 前端交互

路线结果区增加三个正式按钮：

- 最短路径；
- 风景优先；
- 平坦优先。

默认游览推荐显示“智能推荐”状态。点击某个按钮后只高亮该策略；用户可恢复智能推荐。按钮和键盘快捷键调用同一重算函数，不能保留两套实现。

出行方式按钮与策略按钮相互独立：

- 改出行方式不改变策略、起终点或约束；
- 改策略不改变出行方式、起终点或约束；
- 驾车模式仍可显示平坦按钮，但若坡度对驾车成本无定义，按钮禁用并说明原因，不得清除其他路线状态；
- 请求进行中重复点击采用最新请求生效原则，旧响应由 `requestSeq` 丢弃。

## 10. 路由性能

### 10.1 预处理

程序加载路网后准备并缓存：

- 步行、骑行、驾车三张静态模式图；
- 每条边的距离归一化、坡度分量和景观分量；
- 数据指纹和静态图版本。

动态路况、用户硬约束和本次策略作为查询层覆盖，不修改共享静态图。

### 10.2 查询复用

- `shortest` 只执行一次长度 Dijkstra；
- 多因素路线复用已准备的模式图和边成本分量；
- via 的各段和直达基线共享同一个查询上下文；
- tour 的距离矩阵和逐段规划共享模式图、路况快照、约束和成本分量；
- 固定策略结果可以按数据版本、路况版本、端点、方式、策略和硬约束缓存；画像连续权重不建立无界缓存。

### 10.3 可观测性

服务端分别记录：

- Agent/模型耗时；
- 工具调用耗时；
- POI 解析耗时；
- 路网准备耗时；
- 路径搜索耗时与搜索次数；
- 总响应耗时。

论文实验据此区分语言模型开销和路径算法开销。性能验收以“纯最短只搜索一次、同一复合任务不重复静态路网准备、交互重算不经过 LLM”为结构性门槛。

## 11. 错误处理

- 目标方式不可达：保留旧路线，说明该方式不可达；
- 硬约束导致不可达：不得静默放宽，要求用户明确修改约束；
- 路况版本变化：按最新版本重新规划，并在状态中返回新版本；
- 快照字段缺失或版本不兼容：返回结构化 `invalid_route_state`，不使用默认珞珈门—樱顶代替；
- 模型或 Agent 不参与按钮重算，因此模型失败不影响已展示路线；
- 任何失败不得部分更新模式、策略、起终点或上下文。

## 12. 研究就绪门槛

进入论文正式自动化评测前，必须满足：

1. 普通通勤走严格长度最短分支；
2. 游览默认、画像、自然语言和按钮的优先级可从响应中追溯；
3. direct、via、tour、multimodal 在方式与策略切换后保持任务结构；
4. 切换失败保留上一条成功路线和上下文；
5. 多轮修改起点、终点、方式、策略和硬约束不发生槽位串改；
6. 画像不再从超时自动采纳学习，通勤结果不污染游览画像；
7. 绕行上限实际约束输出路线，不只是结果标记；
8. 路由耗时与 Agent 耗时可以分别记录；
9. 代码版本、模型、提示词、任务卡、画像状态、校园数据和路况版本均可冻结；
10. 现有校园数据发布门槛继续独立执行，自动化通过不得表述为道路已经现场验证。

## 13. 后续正式评测

本设计完成并冻结研究版本后，再创建和启用 `whu-agent-evaluation` Skill。该 Skill 首先检查上述研究就绪门槛，然后运行：

- 完整 Agent 与 shortest、rule pipeline 等基线对比；
- 无上下文、无画像、无任务卡、无主动澄清等消融；
- 端到端任务完成率、硬约束违反率、工具调用正确率、多轮保持率、故障恢复率、路线代理指标和耗时指标；
- 结论—证据对应表和失败案例清单。

当前阶段只做开发期检查，不把持续变化的开发版本结果作为论文最终实验数据。没有真实用户研究时，只能报告自动化任务表现和系统可靠性，不能声称主观满意度或用户体验显著提升。

## 14. 范围边界

本阶段包含路线策略、画像、状态一致性、确定性重算、按钮交互、性能准备和研究就绪检查。

机载影像拥堵识别、完整管理端重构、全量校园道路现场核查和正式用户研究属于独立工作包。它们可以在数据与实验条件具备后接入统一路线状态和评测框架，但不阻塞本阶段实施。

平坦与风景策略的数据前置工作按 [坡度与景观路段属性主库设计](2026-09-27-slope-scenery-master-data-design.md) 执行。普通通勤的 `shortest` 可以先完成；`flat`、`scenery` 和画像推荐只有在属性主库达到对应数据发布门槛后才能进入正式论文实验。
