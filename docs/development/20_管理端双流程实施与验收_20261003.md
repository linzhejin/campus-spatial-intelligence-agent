# 管理端双流程实施与验收（2026-10-03）

## 目标和范围

管理台保留两条工作流程：人工道路事件管理，以及机载影像巡查与候选复核。影像线索只有在管理员确认具体候选、重新选定实际道路、填写现场核实依据并明确选择事件类型后，才能进入道路事件发布流程。观察区域参考点和车辆像素框不能自动视为地面道路位置；影像任务本身不改变用户路线。

沿用现有 Flask、PostgreSQL 影像任务、JSON 路况文件和 `/manager` 页面。普通用户只接收已发布且当前生效的事件；管理台可查看待生效、已结束和已撤销的记录。

## 已实施

- 管理台提供道路事件、影像巡查、事件记录三个清晰入口。已确认的影像候选可以转入道路表单；表单会清空旧道路和旧事件类型，要求重新选路与说明核实渠道。服务端重新吸附路段，验证影像任务及具体候选状态，保存任务 ID、候选序号、核实依据和发布者来源。
- 影像审核必须指定具体候选并填写文字依据；确认和排除均为一次性决定，保留审核时间、备注和操作来源。定时刷新不会清掉正在输入的审核备注。
- 道路事件的创建、更新、结束和撤销写入操作记录。撤销即时停止影响路线，同时保留事件和来源以供核查。公开路况接口不返回内部审核和来源字段。
- JSON 写入使用跨进程锁与原子替换，避免两个 Web 进程的写入互相覆盖。生产环境首次迁移时先停止旧 Web 进程，再复制既有事件到 Git 管理之外的运行目录；后续部署不覆盖运行文件。已配置的运行文件若丢失，路线与事件接口拒绝按“无事件”继续运行。
- 管理员网页登录有 30 分钟无操作和 8 小时最长会话期限。影像任务的自动轮询和轮询触发的预览媒体请求都不延长无操作期限。视觉任务的存储异常不会向前端暴露数据库连接信息。
- 影像候选进入人工审核前必须符合受限候选结构：类型来自当前识别器支持集合、要求人工审核且禁止自动发布。确认审核和后续关联道路事件都会校验，防止不完整历史任务越过人工复核边界。
- 首次路况文件迁移先校验完整记录，再写入同目录临时文件、同步落盘并原子替换；已有运行文件也会先校验，损坏文件会阻止部署继续，保留原文件供恢复。

## 验收口径

1. 手工事件：管理员登录、选路、选择实际影响类型、查看预览、发布；普通用户只看到生效事件。结束、撤销及过期事件不得继续影响路线。
2. 影像交接：审核明确候选并写依据后，管理员可打开道路表单；来源标识不能跳过人工选路与现场核实。不存在、未确认、歧义候选及缺依据的来源均拒绝发布。
3. 数据可靠性：旧记录可读，撤销和操作历史可追溯，进程并发不会丢失事件；生产首次迁移不丢失旧 Web 进程尚未写完的变更。
4. 权限：写操作要求管理员身份，网页写操作还要求 CSRF；会话到期后返回登录页。

## 限制

- 当前共享管理口令只能把操作者记为 `web` 或 `token`，不能证明具体个人身份。正式多人管理和责任追踪需独立账号或学校统一身份认证。
- 单图车辆密集和视频低速聚集仍是待核实线索，事故识别未上线；没有武汉大学现场影像真值，因此不能宣称已验证的现场检测准确率。
- 本次线上检查以健康、权限、迁移、只读事件和影像 readiness 为主，不在生产环境造假的管制事件。
